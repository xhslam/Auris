# Auris × VMark 当前功能与技术差异报告

> **生成时间：**2026-08-20（GMT+8）
> **VMark 基线：**`xiaolai/vmark` `main` @ `31213f161556e1ab82bc8e39c478389f6cf3e917`，版本 **v0.9.44**。
> **Auris 基线：**本地 `main` @ `a3ada3bab75b8bdfac32f587e863c633ea1d4521`。
> **检查方式：**仅做本地只读 Git/源码核查；未修改 Auris 的功能源代码、未提交或推送任何改动。

## 一、结论摘要

VMark 和 Auris 的共同底座已经很接近：二者都是本地优先的桌面工作区，都采用 React、Zustand、ProseMirror/CodeMirror 类编辑技术，并都有受管浏览器、MCP 与工作流能力。**真正的差异不在“有没有编辑器或浏览器”，而在两款产品管理什么对象。**VMark 管理的是通用工作区中的 Markdown 文档、文档间依赖和可交付出版物；Auris 管理的是语言学习过程中的视频、音频、词汇、句子、复习与学习笔记。[1] [7]

本轮最应纳入 Auris 产品路线的并非整仓移植，而是三项可独立落地的能力：**跨平台 PDF 交付、文档一致性/陈旧性追踪、面向浏览器的本地知识库发布形态**。其中，PDF 是最明确的用户可见缺口；一致性层是最有长期复利、但也最不应仓促照搬的能力；知识库服务适合作为笔记与学习材料的“阅读/检索出口”。反过来，VMark 在 8 月 19 日新增的浏览器工作流录制并不构成 Auris 的明显缺口：Auris 已有同类录制、脱敏、显式确认和执行策略，且安全约束更具体。[2] [4] [10]

| 结论 | 判断 | 依据 |
|---|---|---|
| **P1：PDF 导出** | Auris 存在直接、可感知的功能缺口 | VMark 已有跨平台 PDF 大纲与页码；Auris 当前导出实现只生成 HTML。 [5] [8] |
| **P1：文档一致性层** | Auris 仅有“学习来源归属”，没有“版本化依赖、陈旧检测和处置闭环” | VMark 有 `status`、`breakdown`、`resolve` 等一致性命令；Auris 当前血缘函数仅汇总来源笔记、单词、句子和会话。 [3] [9] |
| **P2：本地知识库服务** | 形态有差距，核心图谱能力已有基础 | VMark 以本地内容服务把工作区提供为可浏览知识库；Auris 当前以应用内关系图和 backlink 为主。 [1] [12] |
| **无需追赶：浏览器录制** | Auris 已达到同等目标，且对敏感输入限制更强 | 两者都把录制结果编译为可复用流程；Auris 会剥离 URL 凭据、查询参数和哈希，且敏感输入永不能写为文本字面量。 [4] [10] |

> **核心判断：**对齐应以“学习笔记与学习产物是否更可靠、更易交付、更易回看”为验收标准，而不是复制 VMark 的界面、Tauri 模块或通用编辑器产品定位。

## 二、追踪状态与本轮新增观察

上一份同步快照把 `e1eea490`（v0.9.6）记为比较提交，但当前 VMark `main` 并不包含该提交。完整本地历史核验显示，两者有共同祖先 `6c238ba7`，旧快照侧独有 1,337 个提交，当前 `main` 侧独有 2,467 个提交。因此，**旧快照不能再作为线性增量的可信基线**；这只说明两个历史线已分叉，不能据此断言上游发生了何种重写操作。应在下一次自动同步前，以本报告记录的 `31213f1` 重新锚定基线。

从 2026-08-17 至本报告的当前提交，VMark 的实质性增量集中在两个方向。其一是 PDF 交付链：跨平台目录（PDF 阅读器侧栏 TOC）和页码设置均已补齐，且将原先 macOS 专用实现替换为基于 `lopdf` 的统一处理路径。[5] [6] 其二是受管浏览器链：点击效果验证、URL 条件等待、导航门控、控制台异常采集、阅读模式提取、运行级审批、流程执行与录制、AI 隔离数据存储均在同一批次完成。[2] [4]

| 本轮上游变化 | 给用户解决的问题 | 对 Auris 的结论 |
|---|---|---|
| PDF 目录与页码 | 让长文导出的 PDF 可导航、可引用、可打印，而非只有一张视觉正确的页面 | **应跟进。**Auris 目前的 HTML 产物可作为渲染输入，但缺少最终文件交付层。 |
| 浏览器流程录制与重放 | 将重复网页操作变成可审阅、可重放的流程，同时不记录输入值 | **已基本对齐。**Auris 现有实现可继续做真实 UI/回归验证，而不是重写模型。 |
| 阅读模式 Markdown 提取 | 把网页正文变成可供 AI 阅读/笔记整理的受限、可审计文本 | **选择性对齐。**Auris 有 `clean-reader` 模块；若当前产品需要“浏览即入库”，可补齐站点适配与输出契约。 |
| 非 macOS 原生标题栏适配 | Windows/Linux 用户不再看到重复标题栏、错误文件名或布局留白 | **低优先级。**Auris 使用 Electron，应独立按 Electron 窗口模型处理，不能迁移 Tauri 修复。 |

## 三、功能差异：能力、问题与建议

### 3.1 可交付导出：PDF 是当前最明确的用户价值缺口

VMark 已将 Markdown/HTML 渲染进一步接到三平台 PDF 输出，并在 PDF 中补上目录树和页码。该能力解决的是用户完成笔记、报告或学习总结后，需要一个**不依赖 Auris、不依赖浏览器、可打印和可提交**的稳定文件。其关键不只是“生成 `.pdf`”，而是纸张、边距、分页、CJK 标题、目录、页码和平台行为的一致性。[5] [6]

Auris 当前 `buildNoteHtmlExport` 使用 MarkdownIt 与 KaTeX 输出完整 HTML，包含表格、图片、自定义 CSS 和 `@page` 边距；其中 Mermaid 仍以 `<pre>` 占位，不是可交付的图表渲染。现状已经提供了可靠的 HTML 中间表示，但并没有 PDF 写入、打印调用、分页校验或 PDF 导航树。[8]

| 项目 | VMark | Auris 当前状态 | 所解决的问题 | 对齐建议 |
|---|---|---|---|---|
| HTML 导出 | 有 | 有 | 便携阅读与分享 | 保持现状，作为 PDF 的渲染输入。 |
| PDF 文件生成 | 有，三平台统一交付目标 | 无 | 报告、作业、简历、学习总结的正式提交 | 先定义独立的 `PdfExportSpec`，再由 Electron 主进程负责生成，而不是在 React 页面中拼装。 |
| PDF 大纲 | 有，按标题生成侧栏目录 | 无 | 长文快速定位章节 | 从 Markdown 标题/文档大纲生成书签；需特别测试中文标题和跳级标题。 |
| 页码 | 有，可配置 | 无 | 打印、引用、评阅和分页阅读 | 以页边距、纸张大小、方向为固定输入，不接受“浏览器实际打印结果碰巧正确”。 |
| Mermaid 交付 | 图表会进入 PDF 渲染链 | 当前 HTML 仅保留 Mermaid 源文本容器 | 让图表成为交付物而不是编辑器里的预览 | 在导出前预渲染 SVG/位图，并为失败情况提供明确降级。 |

**技术差异。**VMark 的桌面壳是 Tauri/Rust，近期 PDF 工作使用平台打印管线，并以 `lopdf` 处理跨平台 PDF 大纲和页码。[5] [6] Auris 是 Electron/Node 架构，正确的实现方向应是以 Electron 主进程作为系统能力边界，复用现有 HTML 产物，建立纸张规格、资源加载、字体、Mermaid 渲染和输出路径的显式契约。不要移植 Rust 或 Tauri 绑定；应移植的是 **PageSpec、渲染回归样例和跨平台验收矩阵**。

### 3.2 文档一致性层：从“来源注释”升级为“需要复核的依赖”

VMark 的 Coherence 层把“AI 或人工写当前文档时读过什么”变为可追踪依赖：依赖边绑定修订版本，上游变化后可标记为 stale/diverged，界面通过 Breakdown 列出受影响内容，并由人工选择接受新版本、修订或豁免；该层也向 MCP 暴露状态、边关系与处置入口。[3] [4] 这解决的是一个典型问题：当学习总结、课程笔记和 AI 生成卡片不断复用彼此时，用户无法判断“哪一篇结论已经依据过时材料”。

Auris 目前的 `learning-asset-lineage` 是有价值但不同的语义：它确定性汇总一条学习笔记来自哪个会话、哪些源笔记、单词和句子，并以 `## Asset Lineage` 区块写进产物。[9] 它解决的是“这条学习材料来自哪里”，但尚不解决“上游已更新后，这条产物是否需要重读、哪些下游会受影响、为什么允许暂不处理”。

| 维度 | VMark Coherence | Auris learning asset lineage | 用户问题 | 结论 |
|---|---|---|---|---|
| 依赖对象 | 文档、声明、上下文、变换与版本 | 会话、源笔记、单词、句子 | 看清产物来源 | Auris 已覆盖学习来源。 |
| 版本钉住 | 依赖连接到修订状态 | 未见来源版本或内容哈希 | 防止“来源变了但下游不知情” | **核心缺口。** |
| 变化诊断 | stale/diverged、状态/Breakdown | 未见陈旧状态 | 找出需要复核的学习笔记 | **核心缺口。** |
| 人工处置 | 接受、修订、豁免及理由 | 无处置工作流 | 防止静默覆盖与长期悬置 | **核心缺口。** |
| 语义判定 | 可对冲突/主张做检查 | 无 | 降低纯字符串比对的误报 | 后续能力，不应作为第一阶段阻塞项。 |

**建议的 Auris 最小版本。**第一阶段不应照搬 VMark 的完整主张图或 Rust/SQLite ledger。可先对“学习笔记 ← 源笔记/视频摘要/词表批次”保存内容哈希、创建时间与关系类型；上游发生实质内容变更时，只把下游标为“待复核”，并提供“已复核/暂缓（填理由）”两种状态。这样先解决真正的学习问题：**复习材料是否仍基于我现在认可的源内容**。稳定后再考虑自动语义判断、跨工作区合并和 AI 代办。

### 3.3 本地知识库：图谱已有，面向浏览/检索的服务形态仍缺

VMark 的内容服务将工作区作为本地知识库提供，围绕 wiki-link、关系图、全文搜索、实时刷新和浏览器查看组织内容。这个形态解决的是笔记规模增大后，“我记过什么”和“相关材料之间如何跳转”只能困在单一应用窗口里的问题。[1] 其价值在于把编辑器内的文档关系转成可以独立浏览、检索和演示的阅读面。

Auris 不是没有关系能力。当前关系图模块明确复用 backlink 与 wiki-link 解析，编辑器、阅读渲染和关系图都包含链接解析逻辑。[12] 但本轮未发现一个等价的、专门对外提供 Markdown 知识库页面与搜索的内容服务。因此差异是**访问形态**，而不是是否拥有图谱数据。

| 能力 | VMark | Auris 当前状态 | 解决的问题 | 优先级 |
|---|---|---|---|---|
| Wiki-link / backlink | 有 | 有 | 在笔记中建立可跳转关系 | 无需追赶。 |
| 应用内关系图 | 有 | 有 | 看见关联网络 | 无需追赶；可持续优化学习语义。 |
| 本地内容服务 | 有 | 未发现等价服务 | 将知识库交给独立浏览器阅读、搜索或演示 | P2。 |
| 全文检索阅读面 | 有 | 以应用内能力为主 | 解决“找到写过的内容” | P2。 |
| Slidev/站点化预览 | 有 | 未发现等价能力 | 从笔记直接生成演示/浏览体验 | P3，按真实使用场景评估。 |

技术上，Auris 不应为了此项替换现有笔记工作台。较稳妥的设计是将现有 vault、wiki-link 和图谱解析包装为受限本地内容服务，再由已有的受管浏览器或系统浏览器访问。服务必须设置随机会话能力、回环地址限制、根目录白名单和只读资源策略，避免把本地笔记目录无意中暴露为通用 HTTP 文件服务器。

### 3.4 受管浏览器与工作流：目标对齐，Auris 的安全细节更适合保留

VMark 最新浏览器能力把网页读操作与写操作分离：`browser_read` 负责 ARIA 快照、截图、DOM 查询、阅读模式提取与工作流状态；写操作采用运行级审批、导航门控、效果验证和可取消工作流。录制器将点击和字段编辑录成无值流程，密码与一次性验证码转成人工确认步骤，URL 会去掉查询数据。[2] [4]

Auris 已有浏览器租约、审批、审计、分区、恢复与操作策略模块。其录制器也只接受 HTTP/HTTPS URL、去除用户名/密码/查询参数/哈希；密码、认证和文件输入一律声明为 secret，且这些类别永不能提升为可记录的字面量。编译器随后将内容变成带输入槽位和确认步骤的 Browser Markdown 工作流。[10] [11]

| 对比项 | VMark 当前实现 | Auris 当前实现 | 解决的问题 | 结论 |
|---|---|---|---|---|
| 流程录制 | 新增，输出 value-free workflow | 已有，输出 Browser Markdown | 消除重复网页操作 | **功能已对齐。** |
| 敏感输入 | 密码/验证码要求人工确认 | `password`/`auth`/`file` 永不记录字面量 | 防止凭据写进流程文件 | **保留 Auris 规则。** |
| URL 脱敏 | 仅保留 origin + path | 清空用户名、密码、query、hash | 防止令牌进入审计与工作流 | **Auris 规则更明确。** |
| 控制权 | AI 页、人工页与授权规则 | 租约 epoch、一次性审批、审计、分区 | 防止 AI 越权操控用户页面 | **Auris 架构更适合现有 Electron 外壳。** |
| 网页阅读提取 | reader-mode Markdown + 站点插件 | 有 `clean-reader`，站点适配与对外契约需再验收 | 将网页变为可整理学习材料 | 选择性增强。 |

因此，浏览器部分不建议“按 VMark 重做”。可借鉴其 **可观测性**：明确页面状态回传、点击是否生效的验证、URL 条件等待、失败原因文本化和控制台异常采集；这些会让 Auris 既有安全模型更易诊断，而不破坏 Electron 分区与租约体系。

### 3.5 编辑器与通用格式：以选择性补齐代替全面同化

VMark 仍是一个通用 Markdown 编辑器，覆盖 WYSIWYG、Source、表格、数学、Mermaid、媒体、前置元数据、CJK 输入/排版和多种文本操作。[1] Auris 当前笔记区直接使用 ProseMirror 富文本 schema 与 CodeMirror 6，并具备 wiki-link、backlink、KaTeX、Mermaid 相关渲染与关系图模块。[7] [12] 对学习笔记而言，基础编辑体验已经不是主战场。

| 项目 | 差异 | 解决的问题 | 建议 |
|---|---|---|---|
| WYSIWYG 多光标、通用文本变换 | VMark 更偏通用编辑器深度 | 批量文稿编辑效率 | P3；仅在真实写作痛点出现时移植。 |
| Schema-aware 格式预览 | VMark 对通用项目文件的语义预览更完整 | 阅读 CI、配置、代码仓库文件 | P3；优先做对学习任务有用的格式，如字幕、词表和课程元数据。 |
| CJK 排版/检查 | VMark 的规则与门禁更系统 | 中文写作、标点和空格一致性 | P2；可先做非破坏性提示，不做自动改写。 |
| 编辑器核心 | 实现不同但能力高度重合 | Markdown 与富文本双向编辑 | 不建议迁移 Tiptap；维持 Auris 自研 ProseMirror schema。 |

## 四、技术架构差异

| 维度 | VMark | Auris | 对齐含义 |
|---|---|---|---|
| 桌面外壳 | Tauri v2 + Rust | Electron 41 + Node/Electron 主进程 | 只能移植产品契约和测试思想，不能移植平台绑定代码。 [6] [7] |
| 前端与状态 | React 19、Zustand、Vite | React 19、Zustand、Next.js 16（webpack） | UI 层可互相借鉴，但启动、打包与 IPC 生命周期不同。 [6] [7] |
| 编辑器 | Tiptap/ProseMirror + CodeMirror | 自研 ProseMirror schema + CodeMirror 6 | 共享底层概念，Auris 不需要改变 schema 主权。 [1] [7] |
| 浏览器 | Tauri 原生 WebView 与 MCP 工具分层 | `WebContentsView`、分区、租约、审批、审计 | Auris 的风险模型已深度绑定 Electron，应局部增强而非替换。 [2] [10] [11] |
| 一致性数据 | Rust 一致性内核、索引、追加式记录、MCP 处置命令 | 学习来源区块与领域对象关联 | Auris 需要先定义领域级变更事件与哈希，再引入索引。 [3] [9] |
| 导出 | 平台打印 + Rust PDF 后处理 | MarkdownIt/KaTeX HTML 生成 | Auris 需要补主进程 PDF 输出与回归测试。 [5] [8] |
| 本地数据 | Rust 原生数据与工作区文件 | Next/Electron 本地服务、vault 与学习领域数据 | 可复用 Auris vault，不应复制 VMark 数据层。 [6] [7] |

## 五、优先级与验收口径

| 优先级 | 建议事项 | 首个可用版本的范围 | 验收问题 |
|---|---|---|---|
| **P0** | 重建 VMark 追踪基线 | 将 `31213f1` 写为新锚点；保存本报告的能力映射；后续只比较新的可达提交 | 下次报告能否准确回答“本轮新增了什么”，而不是重新比较整仓？ |
| **P1** | PDF 导出 | 单篇笔记 HTML → PDF；可选纸张/方向/边距；中文字体可用；图片和 Mermaid 可交付 | 一篇含中文标题、公式、表格、图片和 Mermaid 的笔记能否在目标平台打开、打印和阅读？ |
| **P1** | 学习产物陈旧性追踪 | 记录源对象哈希和依赖类型；上游更新后标为待复核；支持已复核与暂缓理由 | 修改源笔记后，系统能否准确指出哪些学习总结、词表或卡片需要重看？ |
| **P2** | 本地知识库阅读面 | 只读内容服务、wiki-link 跳转、全文检索、受限浏览器打开 | 用户能否不进入编辑器也能浏览自己的学习材料，并且服务不会暴露 vault 以外的文件？ |
| **P2** | 浏览器可观测性 | 读取/点击/等待/异常的结构化状态与失败原因；保留现有审批与租约 | 自动化失败时，用户和 Nia 能否知道是授权、元素歧义、导航失败还是页面异常？ |
| **P3** | 通用编辑器增强 | CJK 提示、结构化格式预览、按需多光标 | 这些能力是否真实缩短学习笔记整理时间，而非仅增加编辑器复杂度？ |

## 六、Auris 已有且不应被 VMark 同化的优势

Auris 的产品主线是学习闭环。视频库、音频/跟读、词库、句库、复习、闪念、发音评估以及 Nia 辅助形成了通用 Markdown 编辑器不覆盖的领域能力。即使引入 PDF、知识库或一致性层，也应坚持以下边界：PDF 服务于学习成果交付；一致性服务于材料更新后的复核；知识库服务于复习和回顾；浏览器服务于安全研究与课程资料采集。

这意味着，Auris 不应向“通用开发者 Markdown IDE”转向。VMark 最值得借鉴的是其将复杂能力写成**显式、可验证、可回退的产品契约**：输出规格、状态模型、审批边界、跨平台矩阵和回归测试。Auris 应将这种工程方法用于语言学习工作流，而不是移植它的全部功能表面。

## 七、检查记录与局限

本轮已在本地克隆并核验 VMark 当前 `main`、产品指南、关键提交、技术清单和对应源码模块；同时核验 Auris 的 `package.json`、笔记导出、学习血缘、浏览器租约/审批/审计/恢复模块、浏览器工作流录制器、编辑器和关系图模块。Auris 工作区中原有的 `docs/superpowers/specs/2026-08-18-home-free-canvas-design.md` 未提交改动保持不动。

本报告是功能和架构决策材料，并非完整安全审计或运行时验收。没有启动桌面应用、没有生成 PDF、没有执行浏览器自动化，也没有修改代码；在落实任一 P1 项目前，应单独建立设计说明、测试矩阵和桌面端验收步骤。
